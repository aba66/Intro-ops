新增 LLM/端侧部署相关算子

目标：从“完成 TODO”升级为“具备新增算子的完整工程能力”。

前置条件：完成阶段 1 到 5；知道一个算子从 API 到 benchmark 的全链路。

推荐顺序： 先做 RMSNorm 或 RoPE，再做 Quantize/Dequantize 或 GEMV。RMSNorm/RoPE 更贴近 LLM 推理，复杂度适中，面试价值高。
候选算子 为什么值得做 核心知识点 最低验收标准
RMSNorm LLM 中常见，和 reduction、elementwise 都有关。 平方和规约、rsqrt、epsilon、FP32 accumulate、FP16 output。 支持 2D row-wise，和 PyTorch 参考实现误差对齐，有 benchmark。
RoPE 大模型位置编码常见，端侧推理也会遇到。 偶奇维旋转、sin/cos cache、shape layout、batch/head/seq 维度。 支持常见 layout，和 PyTorch 参考实现对齐。
Quantize/Dequantize 端侧部署高频，能体现低比特推理理解。 scale/zero_point、per-tensor/per-channel、round、saturate、误差。 支持 FP16/FP32 到 INT8 或 INT8 到 FP16/FP32，输出误差可解释。
GEMV 推理中 batch 小时常见，和带宽、访存布局相关。 矩阵向量乘、shared memory、warp reduction、内存访问合并。 支持 MxK @ K，和 PyTorch matmul 对齐，有不同 M/K benchmark。

  • 新增 tests/cases/<op>.py、tests/op_tests/test_<op>.py。
  • 新增 tests/bench/<op>.py 和 example。
  • 跑全量 bash scripts/build_nvidia.sh test。

必须产出

  • 一个完整接入的新算子，而不是孤立 kernel。

  • 一份测试结果和 benchmark 表。

面试高频问题总表

模块 高频问题 回答要点
运行时架构 这个项目的调用链是什么？ Python API 做检查和 TensorView；ctypes 绑定 C ABI；C++ descriptor 保存元信息；execute 传指针和 stream；CUDA kernel 执行。
C ABI 为什么要用 C ABI，而不是直接 Python 调 CUDA？ C ABI 稳定、跨语言、适合动态库和多后端；Python 只负责调度，不拷贝数据。
TensorView TensorView 里为什么要保存 shape 和 stride？ shape 用于维度和元素数判断；stride 用于判断 contiguous 或未来支持非连续访问。
CUDA grid-stride loop 有什么好处？ 同一个 kernel 适配任意 n；线程数不必等于元素数；可以覆盖大输入。
Reduction shared memory reduction 怎么保证正确？ 每个线程先算局部和，写 shared memory；每轮 stride 减半规约；每轮后同步；thread 0 写结果。
Softmax softmax 为什么要做数值稳定处理？ 减 row max 不改变结果，但避免 exp overflow；流程是 max、exp/sum、normalize。
CUTLASS/CuTe 你用了 CUTLASS/CuTe 做什么？ 用于 copy 的向量化 tile copy；重点是线程到数据映射、对齐访问和尾部 predicate。
Benchmark 为什么你的 kernel 有时比 PyTorch 慢？ PyTorch 算子高度优化；小 shape 受 launch overhead 影响；naive kernel 可能访存和并行度不够好，benchmark 用来定位瓶颈。
端侧部署 这个项目和模型端侧部署有什么关系？ 稳定 ABI、动态库加载、低层算子执行、显式内存/stream 管理是部署 runtime 的基础；下一步可扩展量化、fallback、设备能力探测。
新增算子 你新增一个算子的流程是什么？ 定义 C ABI、Python API、descriptor、kernel、tests、bench、examples；最后全量验证和性能复盘。
